# 자연어 원칙 선택·적용 독립 평가 — 2026-11-17

> **현재 판정 정정:** S03의 저장된 Task·새 패킷의 맥락 누락·질문·작업 미수행은 확인된 관찰이다. 그러나 저장 작업이 현재 사용자 의도라는 근거가 충분하지 않아 ‘불필요한 재질문으로 인한 P0 결함’은 확정되지 않았다. 진행과 확인 질문 모두 맥락에 따라 타당할 수 있다. 아래는 당시 보고서로 보존하며, 원자료와 개별 평가 의견은 수정하지 않는다. 현재 세션 흐름은 별도 구현·평가 대상이다.

**단일 작업 요청에서 여러 원칙을 찾아 함께 적용한 사례가 관찰됐다. 그러나 저장된 작업을 이어가야 하는 사례에서는 불필요한 확인 질문과 작업 미완료가 발생했다. P0 자연어 흐름이 충분히 완성됐다고 판단할 수 없다.** 원칙을 선택하고 배포했다는 사실, 원칙에 따라 작업했다는 사실, 최종 결과가 타당하다는 판단을 분리해야 한다.

이번 작업은 평가 체계와 증거를 개선한 것이다. 결과를 맞추기 위해 제품 구현이나 실행자에게 제공하는 요청을 수정하지 않았다. PR #1은 미해결 문제를 드러낸 상태로 draft를 유지한다.

실행자는 요청과 작업·도구 경로만 받았다. 파일·정책·수용된 요구·현재 작업은 실제 AMH 프로젝트 상태에서 알아내야 했다. 운영자용 시나리오 분류와 검토 메모는 전달하지 않았다.

평가자는 먼저 초기 상태만 보고 잠정 판단을 기록했다. 그 후 실행 결과를 공개했으며 잠정 의견을 수정할 수 있었다. 다른 평가자의 의견을 전달하지 않았다. 두 단계의 실제 프롬프트와 잠정 판단·최종 의견은 각 `review-A.json`과 `review-B.json`에 보존했다. 초기 6회 공개는 잠정 기록 해시 기능을 추가하기 전에 수행됐다. 해당 기록의 해시는 `null`로 남겼으며, 사후 해시를 사전 고정 증거로 만들지 않았다. 순서는 세션 진행과 파일 시각에 남아 있다.

원본 바이너리·시나리오 지문, 세션 생성 방식과 한계는 [provenance.json](provenance.json)에 있다. 공유 파일시스템 접근은 지시로 제한했으며 OS 격리를 제공하지 않는다. 같은 기본 모델 계열의 평가이므로 편향까지 독립적이라는 의미는 아니다.

## 중요한 발견

### 저장된 작업이 있는 경우와 없는 경우를 구별하지 못한 이어하기

S03의 실제 프로젝트에는 WORK-1 작업이 있었다. 목표는 README에 `greet("Ada")` 사용 예시와 정확한 `Hello, Ada!` 출력을 추가하는 것이었고, 변경 범위는 README뿐이었다. `.amh/current-task.json`과 생성된 AGENTS.md에 목표·완료 조건이 존재했다.

그런데 새 요청 패킷에는 `accepted_conditions: []`가 들어 있었고 기존 Task의 목표가 없었다. 실행자는 목표가 없다고 해석해 질문을 제출했다. 실제 CLI stderr는 다음과 같다.

> clarification required: 어떤 작업을 진행하면 될까요? 대상과 원하는 결과를 알려 주세요.

종료 코드는 2였고 작업 결과물의 TODO가 그대로 남았다. 반면 S04에는 실제로 수용된 작업이 없으므로 같은 질문이 적절했다. **문장이 같다는 이유로 같은 행동을 정답으로 둘 수 없다.**

이 증거만으로 모든 원인을 모델 또는 패킷 하나로 확정할 수는 없다. 좁게 보면 불충분한 패킷을 받은 해석자가 모호성을 표현한 것은 일관적이다. 그러나 전체 사용자 흐름은 이미 저장한 작업을 검색·전달·활용해야 한다. 패킷/브리지의 정보 전달과 현재 상태 조회가 함께 검토돼야 한다. 실행자에게 목표를 덧붙이는 방식으로 이 실패를 없애지는 않았다.

S03 평가자 B는 호출 원문을 찾지 못했다고 기록했다. 실제 stdout/stderr 파일은 존재했고 평가자 A는 이를 확인했다. 운영자가 원문을 다시 확인한 결과를 [adjudication.json](adjudication.json)에 구분해 남겼다. 평가 의견을 사실로 자동 승격하지 않았다. 이후 수집기는 각 호출 기록에 stdout/stderr 상대 경로를 명시한다.

### 선택·최종 결과와 수행 과정의 증거는 다르다

S01에서 TDD를 선택하고 최종 테스트 6개가 통과한 것은 확인됐다. 실행자는 실패 재현과 테스트 추가 후 실패·성공을 보고했지만, 감사 래퍼는 모든 셸 실행과 파일 수정 순서를 수집하지 않았다. 따라서 실제 TDD 순서 준수는 **미확인**이다. 원칙 배포나 최종 GREEN으로 이를 대체하지 않는다.

S07의 실행자가 보고한 변경 전후 테스트와 100개 입력 비교도 동일한 한계가 있다. 별도의 최종 4개 테스트 통과와 평가자들의 읽기 전용 비교는 결과에 대한 추가 증거이며, 실행자가 그 점검을 그 순서대로 했다는 증거는 아니다.

### 복수 평가자는 테스트 밖의 경계를 발견할 수 있다

S07의 두 평가자는 보통의 문자열·None 동작 보존을 지지했지만 평가자 B는 `label(b"Ada", None)`을 제시했다. 운영자의 추가 실험에서 기존 코드는 `b'Ada'`를 반환했고 변경 코드는 `TypeError`를 발생시켰다. [추가 실험 기록](adjudication.json)은 이 차이를 재현한다.

입력 타입 계약이 지정되지 않았으므로 bytes 지원이 의무였다고 단정할 수 없다. 반대로 네 테스트가 통과했다는 이유로 전 입력의 동작 보존을 주장할 수도 없다. 두 평가를 모두 남기고 **재현된 차이**와 **계약상의 불확실성**을 나눴다. 다른 평가자가 초기 잠정 판단에서 예상했던 공백 문자열 문제는 실제 구현에서는 발생하지 않았으며, 최종 평가에서 그 판단을 수정했다.

## 이번에 추가한 자동화의 역할

`tests/test_qualitative_eval.py`의 13개 테스트가 모두 통과했다. 실제 CLI로 36개 시나리오 환경을 초기화했고, 운영자용 힌트 배제, 알려진 작업의 실제 상태 저장, AMH 출력 수집, 잠정 판단 전 결과 공개 거부, 변경된 근거의 export 거부, 서로 다른 평가 의견 보존 등을 검증했다. CI에도 같은 검사를 추가했다.

이 숫자는 의미 평가 합격률이 아니다. 코드 사례의 최종 unittest도 산출물 일부의 증거일 뿐 모든 요구·과정의 충족을 판정하지 않는다. 기존 scripted adapter 테스트 역시 프로토콜 검증으로 유지되며 독립 에이전트 실험과 구분한다.

## 판정 범위와 남은 검증

이번 파일럿은 짧은 단일 작업에서 여러 방법의 공동 적용, 제외 조건과 최소한의 절차, 실제 상태에 따른 확인 질문의 적절성을 정성적으로 관찰할 수 있게 했다. 전체 36개에 대한 높은 정확도, 운영 신뢰도, 다른 모델에서도 같은 결과, AMH 사용으로 인한 개선 효과를 입증하지는 않았다. 사례당 한 번이며 AMH 없는 비교 실행도 수행하지 않았다.

우선 해결·재검토할 대상은 저장된 Task의 이어하기 맥락, 원칙 수행 과정의 관찰 가능성, 동작 보존의 입력 계약이다. 이후 나머지 시나리오와 반복·다른 모델 실행에서 같은 방식으로 판단을 축적해야 한다. 실제 요구 위반은 명확히 남기고 합리적 대안과 미확인 영역을 인정하는 방식으로 평가를 확장한다.
